# MCP Eventsと認証

[READMEへ](../README.md)

## 公式仕様として確認した範囲

参照元：[OpenAI MCP Events](https://developers.openai.com/plugins/build/mcp-events)。確認日：2026-11-01。以下はこのChatGPT向けプロファイルの整理です。MCP一般や他社製品へそのまま適用できるとは限りません。元になっているMCP Eventsのドラフト仕様本体は未確認です。

全体
- 配信方式はWebhookのみ。ポーリング、ストリーミング、ドラフト仕様の `gap`・`terminated` 制御通知はこの連携では非対応。
- 認証付きMCPに `events/list`、`events/subscribe`、`events/unsubscribe` を実装する。
- dotへ任意の固定URLを使って無認証で送る仕組みではない。ユーザーが監視対象と応答方針を指定し、ChatGPTがその内容で購読する。Slack中継は不要。

`events/list`
- イベント定義ごとに `name`、`description`、`delivery`（例：`["webhook"]`）、`inputSchema`、`payloadSchema` を返す。
- `inputSchema` は購読時に渡される引数、`payloadSchema` は配信する `data` の形を表す。
- 接続中のアカウントが見てよいイベントだけを返す。件数が多い場合は `nextCursor` でページ送りする。

`events/subscribe`
- paramsは `name`、`arguments`（`inputSchema` で検証する購読条件）、`delivery`（`mode: "webhook"`、`url`、`secret`）、`cursor`、任意の `ttlMs`。
- secretは `whsec_` + base64で、デコード後24〜64バイト。
- 購読IDは、認証された利用者、callback URL、イベント名、引数から決定的に導く。同じ購読が来たら更新として扱う（引数は正規化したJSONで比較）。
- 応答は `id`、`refreshBefore`、`cursor`、`truncated`。
- `ttlMs` 省略時はサーバーの既定の寿命、`ttlMs: null` は無期限の要求。サーバーは有限の期限を返し、期限を過ぎたら配信を止めてよい。
- ChatGPTは `refreshBefore` の前に同じ内容で `events/subscribe` を呼んで更新する。更新時に署名secretが差し替わることがある。

`events/unsubscribe`
- paramsは `name`、`arguments`、`delivery`（`mode`、`url`）。冪等にし、接続中のアカウントで認可する。成功時は空の `result`。

callback検証
- 実データの前に、署名付きで `{"type": "verification", "challenge": "<一回限りの値>"}` をPOSTする。ヘッダーは `webhook-id`、`webhook-timestamp`、`webhook-signature`、`X-MCP-Subscription-Id`。
- 2xxで、応答本文の `challenge` が一致した場合（定数時間で比較）だけ配信を有効にする。成功は利用者とcallback URLの組で一定期間キャッシュしてよい。
- 失敗時はJSON-RPCエラー `-32015`（`CallbackEndpointError`）と `data.reason`（例：`challenge_failed`、`timeout`）を返す。
- HTTPS必須。接続時に宛先を解決して検証し、非公開・ローカルのアドレスを遮断し、リダイレクトに従わない。

配信
- エンベロープは `eventId`、`name`、`timestamp`、`data`、`cursor`。トップレベルの `type` は制御通知用で、業務データには使わない。
- `eventId` は再送でも変えず、`webhook-id` ヘッダーにも使う。`timestamp` はイベントの発生時刻（タイムゾーン付きISO 8601）。`data` は `payloadSchema` に従う。
- 署名はStandard Webhooksで、イベントID、署名時刻（Unix秒）、送信する本文のバイト列を対象にする。本文は一度だけシリアライズし、試行ごとに署名時刻と署名を作り直す。
- secretの差し替え時は、短い期間だけ新旧両方の鍵で署名する（スペース区切りの複数署名）。
- 1リクエスト1イベント、本文全体は256 KiB以下。2xxは受領のみで、処理は非同期。ChatGPT側で複数のイベントが1回のタスク実行にまとめられることがある。
- 一時的な失敗は指数バックオフで回数を限って再送する。410と413は再送しない。順序は保証されない。
- 購読の期間中も利用者のアクセス権を確認し、失効していたら配信を止める。

履歴の再開（replay）
- イベント種別ごとに任意。対応する場合は、購読時の `cursor` から、期限切れやサーバー再起動の後に再開する。履歴が残っていなければ `truncated: true` を返す。
- 対応しない場合は `cursor: null` を返し、中断中に取りこぼしたイベントはプロトコルでは回収できない。

公式本文に記載がない点：TTLの最小・最大値、404の扱い、再送の回数と間隔、署名時刻の許容範囲、検証キャッシュの期間、鍵の差し替え期間、履歴の保持期間。

## Pingluneのイベント定義

`events/list` で返すイベント定義は `pinglune.event` の1種類です。dataの形（payloadSchema）は[イベントモデル](architecture.md#イベントモデル)に定めます。業務上の種別はdata内の `type` に置き、エンベロープのトップレベルには置きません。

購読条件は `inputSchema` で次のように定義します。どの条件も任意で、指定した条件をすべて満たすイベントだけを配信します。何も指定しなければ、ワークスペースのすべてのイベントが対象です。ChatGPTはユーザーの指示から引数を組み立てるため、各項目の `description` に意味と例を書きます。

| 引数 | 内容 |
| --- | --- |
| `types` | 種別の配列。いずれかに完全一致するもの |
| `sources` | 送信元の名前の配列。いずれかに一致するもの |
| `labels` | キーと値。指定したすべてのキーで値が一致するもの |

ChatGPTが送信元を内部IDで指定することは難しいため、`sources` は送信元の名前で指定します。このため送信元の名前はワークスペース内で一意にします。`additionalProperties` は `false` とし、未知の引数は拒否します。

## Pingluneの購読・配信設計

購読の受付（`events/list`、`events/subscribe`、`events/unsubscribe`）、callback検証、配信（イベント受付時の配信の作成、Queuesによる送信と再送、管理画面の配信状況）は実装済みです。再送の回数と間隔などの値は[配信の流れ](architecture.md#配信の流れ)に記載します。

- 購読を受ける時点で、利用者が対象のワークスペースのメンバーであることを確認する。MVPでは利用者の個人用ワークスペースが対象になる。
- 購読IDは公式の方式どおり、利用者、callback URL、イベント名、正規化した引数から導く。`sub_` に、これらを正規化したJSONのSHA-256の先頭32桁を付けた値とする。同じIDの購読は更新として扱い、期限と署名secretを更新する。引数の配列の順序と重複は正規化しないため、順序が違えば別の購読になる。
- 購読の寿命は、`ttlMs` を5分以上24時間以下に丸めた値とする。省略時と `ttlMs: null` は24時間。応答の `refreshBefore` は受付時刻にこの寿命を足した時刻で、購読はさらに1時間の猶予の後に期限切れになる。更新が少し遅れても、検証のやり直しや取りこぼしが起きないようにするため。
- callback検証は、新しい購読と、終了済み・期限切れの購読を復活させるときだけ行う。有効な購読の更新では検証しない（公式の「成功を一定期間キャッシュしてよい」に当たる）。
- 更新で署名secretが変わったときは、前のsecretを1時間だけ残し、その間は配信で新旧両方の鍵で署名する。終了済み・期限切れの購読を復活させるときは前のsecretを残さない。
- 署名secretは配信のたびに必要なため、ハッシュではなく暗号化して保存する。AES-GCM（256ビット）で暗号化し、購読IDを追加認証データにして、別の購読の行へ暗号文を移しても復号できないようにする。鍵は新しい設定を増やさずに `JWT_SECRET` からHKDF-SHA256で導出し、JWTの署名鍵とは分ける。このため `JWT_SECRET` を変えると、保存済みのsecretは復号できなくなる。ChatGPTは期限（最長24時間）の前に同じ購読を更新してsecretを渡し直すので、その時点で新しい鍵で保存し直され、配信が回復する。それまでの間、その購読への配信はできない。
- secretは平文でログ、応答、エラーに出さない。
- 履歴の再開（replay）はMVPでは対応せず、`cursor: null`、`truncated: false` を返す。イベントは時刻順に並ぶ `event_id` でD1に保存しているため、後から対応する場合はこれをcursorに使える。
- `events/unsubscribe` は冪等で、該当する購読がなくても空の `result` を返す。購読IDに利用者が含まれるうえ、終了する行も利用者で絞るため、他の利用者の購読は終了できない。引数は購読時のスキーマでは検証しない。スキーマを後から狭めても、以前の購読を解除できるようにするため。
- 購読は削除せず、終了時刻を記録して止める（配信の記録から参照するため）。ユーザーを削除したときだけ、購読の行も削除する。パスワード変更、管理者によるパスワード再設定、セッションの失効では、grantの取り消しと合わせてそのユーザーの購読をすべて終了する。
- 配信の直前に、購読が有効で期限内であること、利用者がワークスペースのメンバーであることを確認し、満たさなければ送らない。
- 配信先の応答が2xxなら成功、410と413は再送せず失敗として記録する。410でも購読は止めない（ドラフト仕様では410は購読に影響しない。購読はChatGPTの更新が止まれば期限で終わる）。それ以外の失敗はQueuesの再試行で指数バックオフにより再送する（30秒から倍々に5回）。
- エンベロープは `{ "eventId", "name": "pinglune.event", "timestamp": 発生時刻, "data": get_eventの結果, "cursor": null }`。`webhook-id` はイベントIDで、再送でも変えない。本文が256 KiBを超えるイベントは送らずに失敗とする。
- `X-MCP-Subscription-Id` ヘッダーに購読IDを入れる。

JSON-RPCのエラーはChatGPTの記載に合わせます。引数の誤り（未知のイベント名、`webhook` 以外の配信方式、不正なURLやsecret、購読条件の誤りなど）は `-32602`（`Invalid params`）、callbackの宛先が遮断対象・到達できない・検証に失敗した場合は `-32015`（`CallbackEndpointError`）、想定外のエラーは `-32603`（`Internal error`）です。`-32602` と `-32015` では `data.reason` に理由（例：`invalid_url`、`blocked_destination`、`challenge_failed`）を入れます。ドラフト仕様本体のエラーコードは暫定のため使いません。

### callbackへの送信

検証用通信と配信の両方に同じ制限を適用します。送信のたびに次を確認します。

- URLはHTTPSで、ユーザー名・パスワード、443以外のポート、フラグメントを含まず、2,048文字以下。
- ホストがIPアドレスなら遮断する（Workersの `fetch()` はIPアドレス宛てに送れないため、公開アドレスでも一律に拒否する）。`localhost`、`.localhost`・`.local`・`.internal`・`.home.arpa`・`.lan` で終わる名前、ドットを含まない名前、Pinglune自身のホスト（リクエストのホストと `APP_ORIGIN` のホスト）も遮断する。
- DNS over HTTPS（`cloudflare-dns.com`）でAとAAAAを引き、1つでも公開でないアドレスがあれば遮断する。IPv4はプライベート、ループバック、リンクローカル、CGNAT、文書用、マルチキャスト、予約済みなどの範囲を遮断する。IPv6はグローバルユニキャスト（`2000::/3`）だけを許し、その中の特殊用途・文書用・6to4の範囲も遮断する。名前を解決できないときは送らない。
- リダイレクトには従わず、3xxは失敗とする。タイムアウトはDNS over HTTPSが5秒、送信が10秒。応答本文は4 KiBまで読む。

公式は「接続時に宛先を解決して検証し、検証したアドレスへ接続する」ことを求めていますが、Workersの `fetch()` には接続先のIPアドレスを固定する手段がありません。このため事前にDNS over HTTPSで検証し、そのあとホスト名のまま `fetch()` します。事前の名前解決と `fetch()` 自身の名前解決の間にDNSの答えを変えられると（DNS rebinding）、検証を通った後に非公開のアドレスへ送られる可能性が残ります。互換フラグ `global_fetch_strictly_public` は自分のゾーン宛ての送信をセキュリティ設定に通すためのもので、非公開アドレス宛ての遮断にはなりません。接続先IPを固定するには `connect()` と自前のTLSなどが必要になるため、MVPでは行わず、この残余リスクを受け入れます。

### アクセス権を失ったときの残余リスク

- grantの取り消しはKVで行い、KVは結果整合性のため、取り消しの後も約60秒は古いアクセストークンで `events/subscribe` を呼べることがある。このとき購読は再び有効になる。
- 明示的な取り消し（ユーザー削除、パスワード変更、セッションの失効）以外でアクセス権を失った場合（トークンの期限切れなど）は、購読は期限（最長25時間）まで残る。ユーザーが削除されていれば、配信の直前の確認で送らない。

## 三つの認証境界

| 境界 | Pingluneの設計方針 |
| --- | --- |
| 送信プログラム → 受付 | HTTPはAPIキー、同じアカウントのWorkerはService Bindingsのpropsで送信元を確定し、その送信元が属するワークスペースに保存する |
| dotなど → MCP | OAuth 2.1で利用者を認証し、購読とデータ読み取りをワークスペースのメンバーかどうかで認可する |
| Pinglune → callback | 購読ごとのsecretで署名し、検証済みの送信先に限って配信する |

受付の二つの入口は[受付の経路](architecture.md#受付の経路)を参照してください。HTTPのAPIキーは次の方針です。

- 1つの送信元に複数のキーを同時に有効にでき、キーごとに失効できる。新しいキーへ切り替えた後に古いキーを失効させる。
- 平文は保存しない。`pl_<keyId>_<secret>` の形式とし、keyIdで行を引いてsecretのハッシュを比較する案。secretは32バイト以上のランダム値とする。
- 受付のパスは `POST /ingest/v1/events` とし、Webセッション用の `/api/v1` と分ける（`/api/v1` にかけているCSRF対策の同一オリジン確認は、外部のプログラムから呼ぶ受付にはかけられないため）。
- キーは `Authorization` ヘッダーでのみ受け取り、クエリ文字列では受け付けない。ログに残さない。
- APIキーだけでは同じリクエストの再送を防げないため、重複は重複排除キー（`idempotency_key`）で吸収する。
- 本文の改ざんとリプレイを防ぐHMAC署名は、MVPには含めず、MVP後に実装する予定。

MCPの認証では、MCP認可仕様に沿ったOAuth 2.1の認可サーバーをPinglune自身が持ちます。Librenoの実装（`@cloudflare/workers-oauth-provider` を使ったもの）を流用し、DCR、CIMD、PKCE（S256）、保護リソースメタデータ、認可サーバーメタデータ、RFC 9207のissパラメータに対応します。クライアント、grant、トークンはKVに保存します。CIMDには互換フラグ `global_fetch_strictly_public` が必要です。

認可サーバーと同意画面に加えて、人のログイン、Webセッション、ユーザー管理もLibrenoから流用します。Libreno固有のページ、フォルダー、添付との結合は切り離します。

- ログイン方法は環境変数 `AUTH_MODE` で選び、パスワード方式とOIDC方式の両方を持つ。OSSとして公開する可能性があるため、片方に絞らない。
- 複数ユーザーに対応する。当面の利用者は1人の予定。ユーザーにはadminとmemberの役割がある。
- データはワークスペースごとに分ける。MVPではユーザーごとの個人用ワークスペースだけを扱う（[ワークスペースとラベル](architecture.md#ワークスペースとラベル)）。Librenoの個人用スペースを作る仕組みを、Pingluneのワークスペースとして流用する。
- 使える人の制限は、OIDC方式では `ALLOWED_EMAILS` の許可リスト、パスワード方式では管理者によるユーザー作成で行う。
- `ALLOWED_EMAILS` が空のときはログインを拒否する。Librenoは空のとき全員を通すため、ここは変更する。設定し忘れたインスタンスが全開放にならないようにするため。
- `ALLOWED_EMAILS=*` のときは全員を通し、許可の判断をIdPに任せる。Cloudflare Access for SaaSをIdPにする場合は、Accessのポリシーで許可するドメインやアドレスを管理する。ユーザーの追加はポリシーの変更だけで済み、Pingluneのデプロイは要らない。
- Access for SaaSのポリシーが効くのは、サインオンとセッションの再発行のときだけ。ユーザーを外すときは、Pinglune側でもユーザーを削除してgrantを取り消す。
- ユーザーの削除、パスワード変更、セッションの失効では、そのユーザーのgrantをすべて取り消す。

共通MCPによってR2資格情報をAIへ直接渡す必要はなくなりますが、それだけでは認可は成立しません。data_refの読み取りでも、利用者が対象データのワークスペースのメンバーであることを確認します。購読で見えた参照IDを持っているだけではアクセスを認めません。

アクセス対象と許可操作をcapabilitiesやallowlistで管理する方式は候補です。秘密情報を扱うストレージとログのマスキング方法も未決定です。

## 入力はデータとして扱う

受け付けた原文やイベントのsummaryは、AIへの実行指示として信頼しません。タスクの動作はユーザーが承認した指示と権限で定め、未知のtypeから任意の操作を実行させない方針です。

アクセス権の対応は、信頼済み送信元の認証情報を根拠にします。ラベルや本文にproject-aと書かれているだけでは、そのプロジェクトの調査権限を与えません。確かな送信元は `source` で判断します。最初の調査は読み取りと報告に限定し、DB更新や修復は別途明示的な許可が必要です。
